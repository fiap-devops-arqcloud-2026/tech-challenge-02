Escalabilidade nos Servidores

Como fazer um sistema aguentar milhões de acessos sem cair — em 6 aulas, com o significado de cada sigla, para que serve e um exemplo real do nosso projeto.

Guia de estudo6 aulas+ glossário de siglas+ conexão com o ToggleMaster

O que é escalabilidade?

É a capacidade de um sistema crescer para aguentar mais demanda sem sair do ar. Cuidado: escalar (aguentar mais gente) é diferente de otimizar (deixar mais rápido). Um app que "viraliza" e cai é um caso clássico de falha de escala.

Por que este módulo é especial pra nós

O ToggleMaster é praticamente o estudo de caso deste módulo: microsserviços, apps sem estado (stateless), fila para desacoplar (SQS), cache para aliviar o banco (Redis) e load balancer. Quase toda aula tem um "sim, fizemos isso".

Glossário — o significado das siglas

Todos os termos e siglas que aparecem nas aulas, em uma linha cada.

Escala verticalTrocar por uma máquina maior (mais CPU/RAM). Simples, mas tem teto.
Escala horizontalAdicionar mais máquinas iguais. É o padrão da nuvem (quase infinito).
Load Balancerbalanceador de cargaDistribui as requisições entre vários servidores e desvia dos que estão doentes.
L4 / L7camada 4 / camada 7LB "burro e rápido" (por IP/porta) vs LB "inteligente" (entende URL/HTTP).
Health checkA checagem que diz se um servidor está saudável para receber tráfego.
Statelesssem estadoApp que não guarda dados na própria memória — qualquer cópia atende qualquer usuário. A "regra de ouro" da escala horizontal.
Statefulcom estadoO oposto: guarda dados localmente (ex.: um banco de dados).
Fila / QueueUma "caixa de mensagens" que desacopla partes do sistema e absorve picos.
CDNContent Delivery NetworkRede que guarda cópias do conteúdo perto do usuário, no mundo todo.
Origin / EdgeOrigin = seu servidor original; Edge = os pontos da CDN espalhados pelo globo.
LatênciaO tempo que os dados levam para ir e voltar (quanto mais longe, maior).
CacheGuardar uma resposta pronta por um tempo, para não recalcular/reconsultar.
Read replicaréplica de leituraCópia do banco só para leitura — aguenta muitas consultas.
ShardingPartir o banco em vários pedaços para dividir a carga de escrita.
CAPConsistency, Availability, Partition toleranceTeorema: num sistema distribuído, não dá para ter os três ao mesmo tempo — escolha 2.
ACIDAs garantias fortes dos bancos relacionais (transações confiáveis).
SQL / NoSQLBancos relacionais (tabelas) vs não-relacionais (escala mais fácil, regras mais soltas).
Serverless"Sem servidor": você roda código sem gerenciar máquina (ex.: AWS Lambda, SQS, DynamoDB).
Monolito / MicrosserviçosUm sistema único e grande vs vários serviços pequenos e independentes.
ObservabilidadeConseguir "enxergar" o sistema por dentro: métricas, logs e rastreamento.
SLAService Level AgreementAcordo de nível de serviço (ex.: "99,9% do tempo no ar").
CloudFrontA CDN da AWS.
ELBElastic Load BalancerO load balancer gerenciado da AWS (o que o nosso Nginx criou).
HPAHorizontal Pod AutoscalerCria/remove pods conforme a CPU — a escala horizontal automática do Kubernetes.

As 6 aulas, uma a uma

Cada ficha tem o mesmo esqueleto: em palavras simples, para que serve, um caso de uso e a conexão com o ToggleMaster.

01

Fundamentos de Escalabilidade Moderna

Usamos no projeto
Em miúdos
Escalar = aguentar mais gente sem cair — e isso é diferente de "otimizar" (deixar mais rápido). Há duas formas de crescer.
Siglas e termos
Escala vertical (uma máquina maior — tem teto e fica caro) vs escala horizontal (mais máquinas iguais — o jeito da nuvem). Sempre há trade-off entre performance, custo e complexidade.
Para que serve
Escolher a estratégia certa de crescimento antes que o sistema caia num pico.
Caso de uso
Um app viraliza e milhões acessam ao mesmo tempo → escala horizontal (adicionar servidores) segura a multidão.
No ToggleMaster
Escalamos horizontalmente: mais pods (pelo HPA) e mais máquinas (pelo node group 1→4). É exatamente a escolha da aula.
02

Load Balancers na Prática

Usamos no projeto
Em miúdos
O "maestro" que distribui as requisições entre vários servidores, para nenhum sobrecarregar — e que desvia dos servidores doentes.
Siglas e termos
L4 (rápido, distribui por IP/porta) vs L7 (inteligente, entende HTTP e roteia por URL); health check (checar se o servidor está saudável); algoritmos como round-robin.
Para que serve
Alta disponibilidade (se um servidor cai, o tráfego vai para os outros) e deploys sem downtime.
Caso de uso
5 servidores atrás de um LB; um deles cai e o usuário nem percebe — o LB manda o tráfego para os 4 saudáveis.
No ToggleMaster
Temos dois níveis: o ELB da AWS na frente (criado pelo Nginx Ingress) e o Service do Kubernetes distribuindo entre os pods. O health check são as nossas readinessProbe.
03

Padrões de Escala Horizontal em Arquiteturas Cloud

Usamos no projeto
Em miúdos
Para escalar horizontal de verdade, o app precisa ser stateless (sem "memória" local — a regra de ouro). E as partes devem ser desacopladas com filas, para uma parte lenta não travar o resto.
Siglas e termos
Stateless (sem estado local), desacoplamento, fila de mensagens, resiliência (falha isolada não derruba tudo).
Para que serve
Qualquer servidor atende qualquer usuário; picos são absorvidos pela fila; um componente com defeito não leva o sistema inteiro junto.
Caso de uso
O processamento pesado (ex.: pagamento) vai para uma fila; o resto do site continua rápido e a fila processa no seu ritmo.
No ToggleMaster
Padrão aplicado à risca: nossos serviços são stateless (o estado mora no RDS/Redis/DynamoDB) e usamos o SQS para desacoplar — o evaluation joga o evento na fila e segue; o analytics processa depois.
04

CDNs e Performance Global

Não usamos
Em miúdos
Uma CDN guarda cópias do seu conteúdo em servidores espalhados pelo mundo (a "borda"), para o usuário baixar do ponto mais perto dele — bem mais rápido.
Siglas e termos
CDN (Content Delivery Network), Origin (servidor original), Edge (os pontos de borda), latência, CloudFront (a CDN da AWS).
Para que serve
Entregar conteúdo rápido para usuários em qualquer lugar do planeta e aliviar o servidor de origem.
Caso de uso
Um vídeo ou imagem servido de um edge em Lisboa para o usuário português, em vez de atravessar o oceano desde o Brasil.
No ToggleMaster
Não usamos: nosso sistema é uma API (respostas dinâmicas true/false), não conteúdo estático. CDN brilha em sites com imagens, vídeos e arquivos.
05

Escalabilidade de Banco de Dados

Usamos no projeto
Em miúdos
O banco é o "chefão" da escala — difícil de crescer porque guarda o estado e precisa manter tudo consistente.
Siglas e termos
Read replica (cópia só-leitura p/ aguentar muitas consultas), Sharding (partir o banco p/ dividir as escritas), CAP (não dá p/ ter consistência + disponibilidade + tolerância a falha de rede ao mesmo tempo), SQL vs NoSQL, e o velho amigo cache.
Para que serve
Fazer o banco aguentar mais leituras e escritas sem virar o gargalo do sistema.
Caso de uso
Muitas leituras? Coloca um cache na frente para nem chegar ao banco — ou adiciona réplicas de leitura.
No ToggleMaster
Usamos RDS (gerenciado, permite réplicas), Redis (cache) na frente do evaluation — que é literalmente "escalar leitura com cache" — e DynamoDB (NoSQL) para o analytics.
06

Arquiteturas Escaláveis no Mundo Real

É o nosso projeto
Em miúdos
A aula que junta tudo. Compara os grandes modelos — Serverless, Microsserviços vs Monolito — e mostra como enxergar um sistema gigante (observabilidade).
Siglas e termos
Serverless (código sem gerenciar servidor), Microsserviços vs Monolito, observabilidade (métricas, logs, rastreamento).
Para que serve
Escolher o paradigma certo e conseguir monitorar sistemas com milhares de servidores.
Caso de uso
Um e-commerce monolítico que caiu no pico → quebrar em microsserviços, com load balancer, fila, cache e banco escalável.
No ToggleMaster
Nosso projeto é a resposta desta aula: migramos um monolito (Fase 1) para 5 microsserviços, com LB, fila (SQS), cache (Redis), pedaços serverless (SQS + DynamoDB) e observabilidade básica (Metrics Server + HPA).
