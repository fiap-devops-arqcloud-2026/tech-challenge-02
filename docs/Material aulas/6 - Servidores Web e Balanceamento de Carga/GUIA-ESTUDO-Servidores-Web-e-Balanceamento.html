Servidores Web e Balanceamento de Carga

Como o tráfego é recebido, distribuído e protegido — em 5 aulas, com o significado de cada sigla, para que serve e um exemplo real do nosso projeto.

Guia de estudo5 aulas+ glossário de siglas+ conexão com o ToggleMaster

Do que trata este módulo?

Do "porteiro" da aplicação: o servidor web (Nginx/Apache) que recebe as requisições, o balanceador que as distribui entre vários servidores, e as camadas de segurança e alta disponibilidade que mantêm tudo no ar e protegido.

Por que combina com o nosso projeto

Nosso Nginx Ingress é exatamente o assunto deste módulo. As aulas 1 a 3 (servidor web, balanceamento e Ingress no Kubernetes) são o que fizemos na prática. As 4 e 5 (Istio e WAF) são a evolução.

Glossário — o significado das siglas

Todos os termos e siglas que aparecem nas aulas, em uma linha cada.

Servidor webO programa que recebe pedidos de páginas/APIs e devolve a resposta.
Nginx / ApacheOs dois servidores web mais usados do mundo. O Nginx é leve e ótimo como "porteiro".
Reverse proxyproxy reversoUm "porteiro" na frente dos servidores: recebe tudo de fora e repassa para os de trás.
Forward proxyO contrário: um intermediário do lado do cliente (ex.: o proxy da empresa).
upstreamNo Nginx, o "grupo de servidores de trás" para onde ele distribui o tráfego.
Round RobinMétodo de balanceamento: reveza os servidores em ordem, um de cada vez.
Least ConnectionsManda a requisição para o servidor menos ocupado no momento.
IP HashFaz o mesmo cliente cair sempre no mesmo servidor (persistência de sessão).
Health checkChecagem que diz se um servidor está saudável para receber tráfego.
FailoverDesviar o tráfego automaticamente para os saudáveis quando um servidor cai.
Ingress ControllerO "porteiro" do Kubernetes: lê as regras de rota e distribui o tráfego.
TLS / SSL / HTTPSA criptografia do "cadeadinho" — o tráfego viaja embaralhado e seguro.
cert-managerFerramenta do Kubernetes que emite e renova certificados HTTPS sozinha.
Let's EncryptAutoridade que emite certificados HTTPS de graça (usada pelo cert-manager).
Service Meshmalha de serviçosUma camada que controla toda a comunicação entre os microsserviços.
IstioO Service Mesh mais popular. Coloca um mini-proxy ao lado de cada serviço.
sidecarEsse mini-proxy "de carona" ao lado do app, que intercepta o tráfego dele.
mTLSmutual TLSCriptografia em que os dois lados provam quem são — comunicação interna blindada.
Canary / A/BMandar só uma fatia do tráfego para a versão nova, para testar com segurança.
Observabilidade"Enxergar" o sistema por dentro: métricas, logs e rastreamento (Grafana, Jaeger, Kiali).
HAHigh Availability · Alta DisponibilidadeManter o sistema no ar mesmo quando algo falha.
SPOFSingle Point of FailurePonto único de falha: algo que, se cair, derruba tudo. O inimigo da HA.
WAFWeb Application Firewall"Firewall de aplicação": barra ataques web antes de chegarem no app.
ModSecurity / OWASP CRSUm WAF popular + um conjunto de regras prontas contra ataques conhecidos.
Rate limitingLimitar quantas requisições um cliente pode fazer (freia força bruta e abuso).
SQL Injection / XSSAtaques clássicos: injetar comandos no banco / injetar script malicioso na página.

As 5 aulas, uma a uma

Cada ficha tem o mesmo esqueleto: em palavras simples, para que serve, um caso de uso e a conexão com o ToggleMaster.

01

Servidores Web com Nginx e Apache

Usamos no projeto
Em miúdos
Um servidor web é o programa que recebe o pedido de uma página/API e devolve a resposta. Os dois mais famosos são o Apache e o Nginx.
Siglas e termos
Reverse proxy (um "porteiro" que fica na frente e repassa para os servidores de trás) vs forward proxy (intermediário do lado do cliente); cache; SSL/TLS.
Para que serve
Entregar conteúdo web com desempenho e ter um "porteiro" único que centraliza a entrada, o cache e a segurança.
Caso de uso
Um Nginx na frente de vários apps, cuidando do cache e do HTTPS para todos eles.
No ToggleMaster
Usamos o Nginx (via Nginx Ingress) como o reverse proxy — o porteiro da nossa aplicação no cluster.
02

Balanceamento de Carga na Prática

Usamos no projeto
Em miúdos
Como o balanceador distribui as requisições entre vários servidores — e o que ele faz quando um deles cai (failover).
Siglas e termos
Métodos: Round Robin (reveza igual), Least Connections (manda pro menos ocupado), IP Hash (mesmo cliente sempre no mesmo servidor). Health check, failover e o bloco upstream do Nginx.
Para que serve
Alta disponibilidade: nenhum servidor sobrecarrega e o sistema continua no ar mesmo se um falhar.
Caso de uso
3 servidores no upstream; um trava; o Nginx percebe (health check) e passa a mandar tráfego só para os 2 saudáveis.
No ToggleMaster
O Nginx Ingress + o Service do Kubernetes fazem esse balanceamento entre os pods; o health check são as readinessProbe. Se um pod cai, o tráfego vai para os outros.
03

Gerenciamento de Tráfego no Kubernetes

Usamos (sem TLS)
Em miúdos
O Nginx Ingress Controller como porta de entrada do cluster, roteando por host e caminho (path), e como proteger tudo com HTTPS.
Siglas e termos
Roteamento por host/path, URL rewrite, TLS, cert-manager, Let's Encrypt, ClusterIssuer, HTTPS.
Para que serve
Expor vários serviços por URLs organizadas, de um jeito só, e com certificados HTTPS emitidos e renovados automaticamente.
Caso de uso
/api → serviço A, /web → serviço B, tudo com HTTPS que o cert-manager renova sozinho.
No ToggleMaster
É exatamente o nosso ingress.yaml: roteamos /evaluate, /flags, /rules, /validate e /admin. A única parte que ficou de fora foi o TLS/cert-manager — a demo rodou em HTTP.
04

Controle de Tráfego com Service Mesh (Istio)

Não usamos
Em miúdos
Uma "malha" que coloca um mini-proxy (sidecar) ao lado de cada serviço e assume o controle fino do tráfego entre eles.
Siglas e termos
Service Mesh, Istio, sidecar, mTLS (criptografia mútua entre serviços), VirtualService/DestinationRule, Canary/A/B, observabilidade (Grafana, Jaeger, Kiali).
Para que serve
Controle avançado (canary, A/B), segurança interna automática (mTLS) e observabilidade profunda — em sistemas com muitos microsserviços.
Caso de uso
Mandar 10% do tráfego para a v2 (canary) e ver as métricas de cada serviço numa tela só.
No ToggleMaster
Não usamos — é a camada avançada, além do que o desafio pedia. O nosso Nginx Ingress já resolvia o roteamento que precisávamos.
05

Alta Disponibilidade (HA) e Segurança

Usamos em parte
Em miúdos
Eliminar pontos únicos de falha (nada que, se cair, derrube tudo) e blindar a aplicação contra ataques.
Siglas e termos
HA (Alta Disponibilidade), SPOF (ponto único de falha), failover, WAF (firewall de aplicação), ModSecurity + OWASP CRS, rate limiting, SQL Injection, XSS.
Para que serve
Manter o sistema no ar mesmo com falhas e barrar ataques web comuns antes que cheguem no app.
Caso de uso
Um WAF bloqueia uma tentativa de SQL Injection (devolve 403); o rate limiting corta um ataque de força bruta no /login.
No ToggleMaster
Em parte: temos HA básica (múltiplos pods, 2 nós em 2 zonas, Load Balancer). Mas não montamos WAF, rate limiting nem HTTPS — ficam como evolução de produção.
